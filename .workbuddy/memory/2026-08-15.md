## 候选③ 调查结论（用户选"先查 8 个内联为何 <1×"）
跑 `cargo bench --bench cdl_bench`（Rust-only，N=100k），对照 all161_results_final.csv 的 c_ns：
- 本机 Rust ns/elem 与 final CSV 的 adaq_ns 基本一致（engulfing 1.96≈2.18、separating 4.57≈4.35、hammer 1.71≈1.67），说明 final CSV 仍有效。
- **cdl_engulfing 0.43× = C 侧测量异常**：C 0.93 ns/elem 对"2-candle 极简循环"异常偏低（hammer 的 C 反而 2.76 更慢）。Rust 2.18 属正常；非 Rust 回归。
- **其余 7 个内联 pattern 是真实 Rust-vs-C codegen 差距**：C 在这些轻计算、分支多的蜡烛循环上比 Rust/LLVM 快 1.3–1.8×（separating C 2.49 vs Rust 4.35=0.57；shortline C 2.38 vs 3.11=0.77；harami C 1.86 vs 2.95=0.63）。
- **蜡烛原语已全部 `#[inline]` 单行宏**（real_body/upper_shadow/lower_shadow/high_low_range/candle_color 等，mod.rs L67-98），与 C 宏逐项一致，无安全可消除的冗余计算。
- **结论**：8 个内联 <1× 是硬约束（safe / 无 SIMD / 单线程 / no-deps）下的"诚实地板"——属 Rust/LLVM 对分支 + 递推蜡烛循环的 codegen 劣势。候选③的 macro 不针对该成因（仅触 cdl_harami）。
- **KPI「全量 ≥1×」在当前硬约束下对这 8 个不可达**。唯一可能收复差距的杠杆是：`unsafe get_unchecked` 消除边界检查（违 safe）、或开 SIMD/并行轨（当前延后/单线程）——均需放宽硬约束，属更大架构决策，不在候选③范畴。
- 建议：关闭候选③（或仅做 cdl_harami parity-safe 整洁改写），把"≥1×"目标重新定义为"消除伪慢 + 可并行子集 >2×"，与历史 KPI 修订一致。是否放宽硬约束追 ≥1× 交用户决策。
